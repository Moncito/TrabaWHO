## 1. One-liner

TrabaWho is a Grab-style booking app for blue-collar services (plumbing, electrical, carpentry, aircon, welding). Its AI runs **on the phone**, so a client can turn a messy Taglish problem description into a bookable job, and a worker can produce a job report, **even with no internet**.

## 2. Problem

- Clients don't speak trade language. "Ayaw gumana ng saksakan, nag-spark kanina" doesn't tell them whether they need an electrician, what the job is, how urgent it is, or what it might cost.
- Problems often happen when connectivity is worst: a sparking outlet during a brownout, a leak at night with no load.
- Workers do their jobs in places with bad signal (basements, ceilings, construction sites) and still have to report what they did and what materials they used before they can be paid.
- Booking, matching and payments can wait for the signal to return. Figuring out _what the job is_ and _what was done_ shouldn't have to.

## 3. Target users

| User       | Who                                                                                               | Main need                                                             |
| ---------- | ------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| **Client** | Household or small business in Metro Manila                                                       | Describe a problem in their own words and get the right worker booked |
| **Worker** | Plumber, electrician, carpenter, aircon tech, welder; often prepaid data, mid-range Android phone | Get jobs, and report completed work quickly                           |

## 4. Why local AI (submission answer)

> Home-repair problems happen where signal fails: a sparking outlet during a brownout, a worker inside a basement. TrabaWho's AI runs entirely on the user's phone. It turns a messy Taglish description into a bookable job and writes the worker's job report without data, at no load cost, and without sending descriptions of the inside of someone's home to a server. Booking, matching and sync happen when the connection returns.

## 5. MVP features

Priority: **P0** = must work in the live demo · **P1** = only if P0 is done and stable · **P2** = cut / roadmap slide only.

### 5.1 AI Job Intake — client side (P0, the centerpiece)

**Flow**

1. Client taps **"Ano ang problema?"** and **types** a description in Taglish, Filipino, or English.
2. The on-device model returns a structured result (see 5.1.1).
3. The app shows a **Booking Card**:
   - Service (e.g., Electrician) and task (e.g., "Inspect / replace faulty outlet")
   - Urgency: `EMERGENCY` / `TODAY` / `SCHEDULED`
   - Estimated price range and duration (from the catalog, **not** generated by the AI)
   - Safety note, if a hazard was detected (pre-written, **not** generated by the AI)
   - 1–2 follow-up questions (from the catalog)
   - Short AI summary of the problem
4. The client can **edit** service, task, and urgency before booking. The AI suggests; the client decides.
5. The client types an address (text + barangay) and taps **Book**.
   - **Online:** booking is sent immediately.
   - **Offline:** booking is saved as **Pending — will send when online**, and sends automatically on reconnect.

**5.1.1 AI output contract** (validated with Zod; enum values come from the catalog)

```json
{
  "service": "ELECTRICAL",
  "task": "ELEC_OUTLET_REPAIR",
  "urgency": "EMERGENCY",
  "hazards": ["SPARKING"],
  "summary": "Outlet sa kusina, ayaw gumana at nag-spark.",
  "confidence": "high"
}
```

**Rules**

- `task` must be one of the catalog task codes, or `<SERVICE>_INSPECT` when unclear.
- Code enforces urgency floors: `GAS_SMELL`, `SPARKING`, `BURNING_SMELL`, or `ACTIVE_FLOODING` → `EMERGENCY`; any other hazard → at least `TODAY`.
- If `confidence` is `low`, the card says "Hindi sigurado — paki-check ang service" and highlights the service picker.
- `GAS_SMELL` always shows the evacuation safety note and the 911 hotline, whatever else the model returns.

**Acceptance criteria**

- Works in airplane mode end-to-end up to "Pending" status.
- Correct **service** on at least 17 of 20 and correct **task** on at least 14 of 20 cases in the team's Taglish test set (see 8). Report the real numbers.
- Booking Card appears within **15 s** on the demo phone (verify; target < 8 s).

### 5.2 Booking flow — online (P0, minimal)

1. A booking with status `REQUESTED` is visible to all workers who offer that service in the same city.
2. The first worker to tap **Accept** gets it (server makes sure only one wins).
3. Status flow: `REQUESTED → ACCEPTED → IN_PROGRESS → COMPLETED`.
4. Client and worker see each other's name and phone number, with a **Call** button (phone dialer).
5. Status refreshes by polling every 5 s while the screen is open.

### 5.3 Worker job report (P0, typed)

1. On an `ACCEPTED` or `IN_PROGRESS` booking, the worker taps **"I-report ang trabaho"**.
2. The worker types, e.g., _"Pinalitan ko yung outlet, gumamit ng isang outlet tsaka dalawang metro ng wire, 45 minutes."_
3. The on-device model returns:

```json
{
  "tasksDone": ["ELEC_OUTLET_REPAIR"],
  "materials": [
    { "name": "Outlet (duplex)", "qty": 1, "unit": "pc" },
    { "name": "Wire", "qty": 2, "unit": "m" }
  ],
  "durationMinutes": 45,
  "notes": "Pinalitan ang sirang outlet."
}
```

4. The worker reviews and edits the items and **types the material prices**. The AI never prices anything.
5. Code computes: labor (catalog midpoint) + materials = **total**.
6. Saving works offline. The report syncs on reconnect, and syncing marks the booking `COMPLETED`.

### 5.4 Accounts (P0, demo mode only)

- **No sign-up flow.** Seeded accounts: 1–2 clients and ~10 workers across 5 services, all in one city.
- Login screen is an **account switcher** (pick a seeded user). The app sends the selected user id in an `x-user-id` header.
- Seeded workers show a static "Verified" badge.

### 5.5 Offline model setup (P0)

- The model file (~1 GB GGUF) is **preloaded on the demo phone via adb**. No in-app download for the demo.
- After that, all AI features work in airplane mode.

## 7. Catalog (bundled in the app)

`catalog.json` ships with the app so intake and pricing work offline. Owned by the **AI Engineer**.

- **Services (5):** Plumbing, Electrical, Carpentry, Aircon, Welding.
- **Tasks:** 3 per service plus `<SERVICE>_INSPECT` (20 total). Each task: code, Taglish + English name, min/max price (PHP), min/max minutes, 1–2 follow-up questions.
- **Hazards:** `GAS_SMELL`, `SPARKING`, `BURNING_SMELL`, `ACTIVE_FLOODING`, `NO_POWER`, `STRUCTURAL_DAMAGE`, each with a pre-written safety note in Taglish.

Example rows (**prices are illustrative** and labeled so in the demo unless sourced):

| Code                 | Service    | Task                           | Price (PHP) | Minutes |
| -------------------- | ---------- | ------------------------------ | ----------- | ------- |
| `PLUMB_LEAK_SINK`    | Plumbing   | Fix leak under sink            | 500–1,200   | 30–90   |
| `PLUMB_CLOG`         | Plumbing   | Unclog drain / toilet          | 600–1,500   | 30–120  |
| `ELEC_OUTLET_REPAIR` | Electrical | Inspect / replace outlet       | 400–900     | 30–60   |
| `ELEC_BREAKER_TRIP`  | Electrical | Breaker keeps tripping         | 600–1,500   | 45–120  |
| `AC_CLEANING`        | Aircon     | Aircon cleaning (window/split) | 800–1,800   | 60–120  |

## 8. AI quality: test set and honest reporting

- `eval/intake.json`: 20 Taglish problem descriptions, each with expected service and task. Include vague, mixed and hazard cases.
- `eval/report.json`: 5 worker report texts with expected materials and duration.
- `eval/heldout.json`: 10 extra intake cases written by the SWE **without seeing** `intake.json` or the prompts. Run once, never tuned on.
- `eval/run-eval.ts` runs the model over the sets and prints accuracy and average latency, **plus the same cases with the model switched off (keyword rules only)** and a side-by-side table. Put the **actual** numbers, model name and phone model in the README and pitch.
- The briefing says results can be disputed for **fake benchmarks**. Say plainly that prompts were tuned on `intake.json`; lead with the held-out numbers.

**Current results (Qwen3 1.7B Q4, laptop via Ollama; tuned set):**

| Metric | Qwen3 1.7B (local) | Keyword rules only |
| --- | --- | --- |
| Intake: service | 19/20 | 19/20 |
| Intake: task | 16/20 | 16/20 |
| Report: materials extracted | 4/7 | 0/7 |
| Intake latency (laptop) | ~0.7–1 s | ~0 ms |

**Held-out set (12 cases by a teammate, run once, Oct 9):** service **11/12 model vs 8/12 keywords**; task 4/12 model vs 5/12 keywords; hazards 11/12 (missed "dumidiklap yung saksakan"). Pitch line: the model picks the right *kind of worker* far more often on real messy texts; the exact task is a suggestion the client confirms with one tap.

On the tuned set the two tie on task but fail on **different** cases. The model is the only thing that extracts materials, writes the summary, and handles phrasing nobody wrote a keyword for. That is the answer to "why not just keywords?". The held-out set has to show it.

## 9. Demo script (5 minutes + 3 min Q&A)

Phone screen mirrored to the laptop with `scrcpy` over USB (venue gives HDMI/USB-C to the laptop only). Online parts use our own hotspot, not venue Wi-Fi. The briefing says: prioritize a working product over slides.

1. **(0:00) Hook.** "May sparking outlet ka, brownout, walang data. Sino tatawagan mo?"
2. **(0:30) Online booking.** Wi-Fi on. Client books a plumber. Switch to a worker account, accept, show status change.
3. **(1:30) Airplane mode ON**, visible on screen. Client types the sparking-outlet description. Booking Card shows Electrician, Emergency, safety note, price range. Book → **Pending**.
4. **(2:45) Worker, still offline.** Worker types the job report, gets itemized materials, enters prices, sees the total. Save → Pending.
5. **(3:45) Airplane mode OFF.** Pending booking and report sync; status changes.
6. **(4:15) Proof.** In-app AI stats (on-phone latency, model name), the model-vs-keywords table on the held-out set, "what runs locally" slide.
7. **(4:45) Close** with the "why local" line.
